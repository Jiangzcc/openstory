## 1. 已确认的目标与范围

- 在 OpenStory 开源项目上二次开发，`develop` 承载本项目的二开改动。
- 面向多个租户提供服务；当前完整复用上游 Organization 与共享能力。每用户独立空间和余额仍是未开发的商业规划，不据此裁剪本轮组织功能。
- 界面默认简体中文，支持切换英文；语言记忆和翻译接入已实现，实际覆盖与验收边界见国际化实施记录。
- 首期商业规划按卡密兑换充值，卡密面额、钱包余额、消费报价及扣费统一使用人民币（CNY）；人民币计价与充值结算改造尚未实施。
- 在线支付接入留作后续，保留上游已有 Stripe 实现。卡密按全平台单次兑换、当前用户入账和默认不过期规划，支持自定义面额及预设档位，尚未实现。
- 第三方通过本平台签发的 API Key 直接调用模型暂不纳入首期，未来可能扩展；不因此删除或禁用上游已有的创作 API/MCP。
- 接入包括 fal、OpenRouter 在内的外部模型服务，接入范围可以继续扩展。
- 通过平台收费与供应商成本之间的差额盈利。
- 商业规划不允许用户自带供应商密钥（BYOK），拟由运营方统一提供凭证并按平台余额消费；入口、调用链及结算改造尚未实施，当前组织凭证优先规则保留。
- 允许访问外部 AI 服务；不以完全离线模型部署为前提。
- 分析、设计和交付必须区分上游实现与二开实现。

用户已明确纠正为公网部署，并允许使用 Cloudflare 的部分能力。此前内网独立部署讨论仅保留为历史探索；具体使用哪些 Cloudflare 服务、哪些自建及数据放置仍待技术评估，不把全面运行时迁移或全部 Cloudflare 托管当成已定方案。

## 4. 收费闭环设计建议（尚未实现）

建议围绕如下业务闭环拆分职责，继续复用已有钱包与工作流基础：

1. **充值**：首期由运营方生成并交付卡密，用户兑换后记入钱包；卡密核销与入账需原子、幂等。售卡实收与兑换额度分别理解和记录，在线支付确认是后续扩展。
2. **报价**：根据接入渠道、具体模型、输入/输出单位和任务规格，确定用户价格规则与版本。
3. **预占**：按用户报价冻结可用余额。不能按供应商成本预占，再按更高售价结算。
4. **调用**：服务端解析租户上下文和平台凭证，记录所选渠道；所有重试和轮询沿用该渠道及任务身份。
5. **结算**：按锁定的收费规则、实际有效用量和幂等键确认消费，同时记录供应商成本及其估算/确认状态。
6. **释放与核对**：释放未消费的预占，核对支付与上游账单；供应商成本变化不能直接覆盖用户销售价格或已完成账单。

上述步骤是逻辑职责，不代表已经存在同名表、字段或 Service。首期用户侧使用人民币，金额延续整数记账思路；供应商成本保留原始币种，运营方维护版本化成本换算汇率，用户按模型/规格销售单价结算；记账精度、配置值和技术方案尚待细化。没有实现任何新的汇率、计价倍率或币种迁移。

建议分清以下记录，而不强制现在建立四张新表：

| 业务记录      | 回答的问题                                                                       |
| ------------- | -------------------------------------------------------------------------------- |
| 售卡/收款记录 | 客户实际付了多少，是否已经收到款项？首期可评估人工台账，不把兑换事件直接算成收款 |
| 钱包账本      | 哪个租户入账或消费了多少，是否重复处理？                                         |
| 上游用量/成本 | 哪个渠道的哪个任务产生了什么用量，成本是否最终确认？                             |
| 用户销售账单  | 本次任务适用哪个价格版本，客户应付多少？                                         |

例如，上游成本 1、用户消费 1.3，调用差价为 0.3；它不是净利润。具体售价可固定、按单位或按规则计算，不能在用户未确定计价方式前只修改一个全局常量。

### 人民币计价与供应商成本

已确认：卡密面额、钱包余额、报价、预占、扣费和消费记录采用人民币。以下是实现建议，尚未修改代码或表结构：

- 用户侧使用人民币金额；供应商侧保留原币种用量与成本，另存适用汇率及其版本/时间，换算为人民币成本用于核算。
- 独立的人民币用户售价不等于供应商美元成本。当前首期基准按模型/规格维护人民币销售单价，成本换算和加价倍率可辅助生成售价；任务锁定人民币价格，汇率和供应商账单后续变化不追改已完成消费。
- 模型调用金额可能小于一分钱，内部应保留足够精度的整数单位，并明确舍入规则；不能对每次调用简单按分截断。具体精度属于后续设计。
- 上游 `src/billing/money.ts` 的 Microdollars 明确表示微美元；人民币钱包金额需要明确币种边界，不能通过替换货币符号或复用旧类型完成迁移。
- 如存在历史美元钱包、卡密、流水和预占，需制定明确迁移规则，保留原币种与转换依据；本轮未修改或转换现有数据。
- 本次没有查询或设定实时 USD/CNY 汇率，也没有把某个示例汇率、加价比例或面额档位当成已确定配置。

### 首期卡密方案：上游事实与二开建议

已确认方向是卡密兑换充值；不代表卡密管理与商业安全改造已经完成。

建议业务流程为：运营方发码及交付 → 用户在网页兑换 → 额度记入确定的钱包 → 按平台售价消费 → 查询兑换及消费记录。售卡渠道如何收款另行安排，平台的卡密兑换链路不依赖在线支付回调。

上游事实：

- `createGiftTokenFn` 与 `batchCreateGiftTokensFn` 使用系统管理员中间件；批量接口一次生成最多 500 张、每张 maxRedemptions=1 的码，单张接口支持更多兑换次数。
- 额度入口为 amountUsd、底层为微美元；不能只改界面标签就把它当成人民币或平台积分。
- 同一组织重复兑换由 `(giftTokenId, organizationId)` 唯一键约束；`redeemGiftToken` 使用 `onPrimary` 在主库读取限额，但跨组织总次数仍是先读 count、后写兑换记录。
- `src/billing/server/db/billing.ts` 的 `redeemGiftToken` 在插入兑换记录之后另调 `addCredits`；两者不在同一批原子提交中。
- gift_tokens 当前有金额、最大次数、创建人、过期时间和备注，没有持久化批次实体或手动作废字段；批量生成不等于已实现批次生命周期管理。
- 卡密过期与入账余额有效期是两回事；当前 addCredits 会为入账批次写入到期时间，是否沿用需按产品规则确认。

二开建议与验收重点：

- 首期优先评估固定面额、每码全平台仅兑换一次的付费卡；多租户活动码应与付费卡明确区分。当前尚未把建议变成强制规则。
- 兑换次数限制、核销和钱包入账应形成原子、幂等操作；重点验证跨租户抢兑、同租户重复请求、入账失败/中断后的恢复。
- 运营管理按需要补批次标识、交付、作废、兑换人/归属钱包和操作审计；不把所有管理功能都当作首期已确认范围。
- 设计商用卡密的码强度、兑换限流和查询权限；现有礼品码通过顺序测试并不能证明付费卡可直接上线。
- 发码量、已兑额度、售卡实收、消费收入与上游成本分别统计，避免将免费赠码或未售卡直接记成收入。

### 必须保留或补齐的行为

- 一笔充值确认重试多次只入账一次；浏览器返回成功页不能单独作为入账依据。
- 同一租户并发任务不能重复占用同一份可用余额；工作流重放不能重复扣费。
- 报价、预占、结算使用同一价格语义与版本；任务中途调价不能使同一任务前后使用不同规则。
- 失败时区分上游是否已经收费；按确定的产品规则处理费用，释放未用预占，不能假设所有失败都无成本。
- 供应商成本未知或余额结算不足时进入可追踪异常；不能把告警日志当作商业账单已经结清。
- 成本对账比较供应商成本；不得将用户含差价的扣费与供应商原价直接比较。现有 fal 核对路径涉及交易元数据，改价时需一并验证。
- 不向前端暴露平台上游密钥；租户额度、并发和速率限制与供应商账户额度分别治理。
- 租户隔离验收覆盖网页、RPC、REST、MCP、后台任务、文件与管理端。

## 5. 后续方案与开发顺序（商业闭环仍为规划阶段）

管理员默认模型配置和文本渠道已有源码实现，历史验证状态见各自记录。本次优先完成上游同步及兼容验收；后续商业闭环与部署仍需单独实施，不把文本渠道接入或组织适配等同于商业规则已经完成。

1. **上游同步优先**：完整跟随上游组织、权限、邀请、切换与共享行为，兼容既有国际化、默认模型和文本渠道；实际检查与剩余边界见 [上游合入实施记录](upstream-merge-implementation-20261105.md)。

3. **商业方案与最小闭环（未实施）**：细化人民币记账、卡密、禁止 BYOK 和用户售价；后续在复用 fal/OpenRouter 的链路上实现充值、报价、预占、消费与成本核对。
4. **运营与其他首期规则（未实施）**：继续规划全模型上下架、用户价格、租户限额、异常账单、成本/收入/差价、默认私有媒体与审计；新页面沿用既有翻译机制。
5. **扩展模型与部署验收**：按业务需要扩展渠道；单独验证选定公网环境下的持久化、任务恢复和文件访问；未来接入在线支付时再验收回调网络。

所有后续设计遵守 [扩展与上游兼容约束](extension-policy.md)：保持项目代码风格，优先现有公开接口、独立模块、扩展目录和薄桥接；必要核心修改需最小化并说明原因、影响及升级冲突点，不借隔离二开绕开已有分层。
