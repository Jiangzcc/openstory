# 第一阶段 i18n 开发计划

日期：2026-11-03。状态：登录页样例后，用户已授权全站改造；现有页面与账号验证码邮件已接入。实际覆盖、检查结果与尚需真实业务环境验证的项目见 [全站实施记录](localization-implementation.md)。

本计划落实 [中文界面要求](localization-plan.md)，遵循 [扩展与上游兼容约束](extension-policy.md)。中文界面优先于模型销售计价、成本核算及平台凭证改造；2026-11-06 已取消个人独立人民币余额及新增卡密商业改造，现有组织钱包与兑换卡继续复用。现有账号相关邮件已由用户确认纳入第一阶段。下列批次保留原计划，不能直接当作验收结论；实际实现与验证状态以全站实施记录为准，单页样例另有历史记录。

## 1. 建议采用的方案

登录页样例已采用 **i18next + react-i18next** 作为国际化基础，使用本地中英文资源文件，语言切换控件复用现有 Select；全站计划沿用这一机制。以 **i18next-cli** 作为提取、漏译检查及类型生成的候选开发工具。[S01][S02][S03][S04]

选型理由是尽量保留现有 React、TanStack Start、路由及 Vite 构建方式：通过资源文件、React Provider 和组件翻译调用逐步接入，不额外引入消息宏编译。此判断针对本仓库的改动边界，不代表已经验证性能优于其他库。

样例运行时增加 `i18next@26.7.1`、`react-i18next@17.1.11` 两个固定版本的直接依赖，已核对 peerDependencies、锁文件、类型与构建；i18next-cli 尚未安装，留待提取流程验证后再决定。两个运行时项目的官方许可证均为 MIT；引入时保留相应许可文件。[S09][S10]

先完成“默认中文 → 登录/导航 → 切英文 → 刷新保持 → 切换保留草稿”的垂直验证，再迁移大量页面。国际化库负责语言资源与渲染机制，已有硬编码文案仍需逐处接入；安装依赖不能自动完成全站中文化。

## 4. 工具复用与文案维护

| 复用项                                                  | 用途                                                   | 本期计划                                                                    |
| ------------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------- |
| `useTranslation`、`I18nextProvider`、`Trans` 等公开 API | 普通文本、语言上下文和带链接等富文本                   | 使用官方接口，避免封装另一套翻译语法 [S01][S02]                             |
| i18next 类型扩展                                        | 翻译键、命名空间和插值参数的开发检查                   | 先验证带类型的字符串键；不因可用 selector 就强制全站采用新写法 [S03]        |
| i18next-cli                                             | 提取已有翻译调用、发现硬编码、同步目录、状态与类型生成 | 小样核对自定义目录、别名和动态文本后再加入本地/CI；使用本地资源工作流 [S04] |
| 现有 Select / DropdownMenu                              | 中文/English 切换                                      | 放入现有全局导航或用户菜单，并保证未登录页面可用                            |
| 标准 `Intl` 格式化能力                                  | 日期、数字、相对时间和真实币种的显示                   | 在目标浏览器及 Workerd 中验证；显式保持原有时区与金额语义                   |
| 现有 Vitest / Playwright                                | 资源检查、SSR 和浏览器回归                             | 复用项目测试方式，不引入另一套测试框架                                      |

提取工具可以减少重复劳动，但不能判断每条文案是否属于用户内容、供应商数据或业务提示。自动包装/替换若要使用，只在已列明的文件批次中执行并审查 diff；不运行会连接外部翻译平台的整站自动本地化流程。

维护规则建议如下：

- 按用户确认，直接使用英文原文作为翻译键，例如 `t('Welcome')`、`t('Sign in or create an account')`；中文语言包保存对应译文，英文语言包保存原文。按领域命名空间区分不同上下文，不另造 welcome、description 等语义键。
- 设置 `keySeparator: false` 与 `nsSeparator: false`，将句点、冒号等视为原文的一部分。上游英文文案改变时，同步更新调用及两种语言资源；资源一致性与英文键/值一致性检查应失败提示遗漏。
- 英文目录保存对应的上游文案，中文目录保存人工校对后的译文；默认中文与维护英文源文案并不冲突。
- 按领域和职责拆分命名空间，避免单个大字典；资源文件同样遵守单文件行数约束。
- 使用插值、复数及富文本消息表达完整句子，不用字符串拼接固定中英文词序；资源不承载业务判断或任意 HTML。
- 运行时允许明确的英文回退以保证可用；已列入验收页面的缺键、缺中文或参数不一致应在检查中失败，不能用回退掩盖漏译。
- 模型/供应商原名、用户命名和原始诊断有明确保留规则；英文扫描白名单记录原因，避免一刀切忽略整个文件。
- 上游新增文案通过扫描和页面覆盖清单跟进，不依赖开发者凭记忆补译。

## 5. 模块与最小接入设计

原方案已在全站实施和 2026-11-04 目录整理时细化，当前实际目录如下；实现范围及验证见 [实施记录](localization-implementation.md)：

```text
src/platform/i18n/
  locale.ts                 语言白名单、默认值及 Cookie 名
  preference.ts             请求或浏览器语言偏好解析
  runtime.ts                接收语言与附加资源的实例工厂
  resources.ts              平台通用资源组装
  labels.ts                 静态标签翻译纯函数
  relative-time.ts          相对时间格式化纯函数
  locales/                  auth/common/mail 中英文资源
src/ui/i18n/
  runtime.ts                应用实例组装，复用平台工厂
  resources.ts              业务命名空间资源组装
  use-*.ts                  React 翻译、语言切换及格式化 hooks
  language-switcher.tsx     使用现有控件的语言切换入口
  head.ts                   页面元信息翻译适配
  localized-head.tsx        切换语言时同步页面元信息
  markdown.ts               文档正文显示适配
  locales/                  按语言和业务命名空间拆分的资源
```

`src/platform` 继续保持领域无关：实例工厂接收附加资源，禁止反向导入 cast、shots、billing 等领域目录。跨领域资源由应用入口组装，不增加平台领域依赖豁免。React hooks 和语言切换组件统一位于应用国际化目录，不再另设 src/platform/ui/i18n。

### 5.1 语言选择和持久化

- 支持语言限定为 `zh-CN`、`en`。没有有效保存值时固定 `zh-CN`，不使用浏览器或请求头偏好覆盖这一规则。
- 建议用一个服务端可读的语言 Cookie 记住当前浏览器；首屏将解析结果交给浏览器初始化，避免 Cookie、localStorage 和浏览器检测器争夺优先级。
- 切换写入建议复用 Start 服务函数作为 API 桥接，校验允许的语言值；Cookie 路径、有效期及环境相关属性集中为配置/常量，无需新增用户字段。
- 具体读取时机和公开 Cookie API 在首批对照现有实现确认；不把本计划中的职责名当作已存在 API。
- 保存失败时给出当前语言下的可见提示，不能默默宣称刷新后会保持。首期不增加账号跨设备同步。
- 沿用当前 URL，不引入 `/zh`、`/en` 路由或重写创作资源链接。

### 5.2 SSR、切换与缓存

1. 服务端按请求解析语言并创建隔离的可变实例；只读目录可复用，当前语言不可作为全局共享变量。[S01]
2. 首屏渲染前准备需要的目录，传递可序列化的语言、命名空间/资源；不直接把 i18next 实例塞进可序列化 loader 数据。
3. 浏览器使用同一首屏语言初始化稳定实例，再完成水合；不能挂载后才从默认英文改成中文。[S01]
4. 切换更新翻译上下文和 `<html lang>`、页面标题等显示信息；保持编辑器、对话框、播放位置和创作状态。禁止以重新加载页面或按 locale 重建应用根节点实现切换。
5. 全局 toast、表单规则、菜单定义及缓存的静态标签在使用时解析语言；原始业务查询数据继续复用，不为切语言清空 QueryClient。
6. 根错误边界、404、Provider 外弹层及独立页面逐项验证，确保错误出现时仍能显示可理解文案，不能假设所有路径都在普通 Provider 内。
7. 检查实际 SSR 缓存响应方式；同 URL 的不同语言结果不得被公共 HTML 缓存混用。不顺带引入新的全站缓存策略。
8. 目录按模块组织，加载策略先求首屏确定；是否分包依据实际构建结果决定，不能声称懒加载减少 Workerd 保留的服务端源码堆占用。

### 5.3 内容和业务边界

- 仅替换静态 UI 文案和已识别的用户提示；不翻译用户输入、剧本、生成内容、模型提示词或已有用户命名。
- 面包屑、下拉选项等混合数据只翻译静态标签，动态名称原样显示；持久化的状态码、枚举值和模型键不因翻译变更。
- 常见错误优先复用实际已有的结构化错误与判断函数，在显示层映射；不存在的错误码/字段不能臆造。未知异常提供通用说明，保留现有诊断可追溯性。
- 切换 locale 仅影响格式，不更改时区约定、余额数值、币种、汇率或单位含义。美元仍按真实美元展示；模型人民币售价与现有钱包的衔接另行设计，不安排人民币钱包迁移。
- 不改生成工作流、模型服务选择、BYOK、权限、支付、数据库结构及商业报价规则。

### 5.4 现有账号邮件

- I0 盘点实际存在的账号邮件触发场景、发送回调及模板；覆盖主题、正文、按钮和已有预览文字，不因本需求新增通知类型。
- 语言在发起账号操作时校验并固定；未选择或无有效值时使用 `zh-CN`。如需异步发送，携带同一次操作的语言，不重新读取后来选择的语言或共享全局状态。
- 复用实际已有的认证回调、模板与发信接口，将选定语言作为最小上下文传入；不臆造上游 locale 参数或新增账号语言字段。具体接口由 I0/I1 核对。
- 邮件使用隔离实例或绑定语言的翻译函数；模板和邮件资源保持服务端边界，不为账号邮件引入浏览器端发信能力或将模板资源整体并入页面目录。
- 保留验证码、验证链接、有效期、认证判断和发送频率等原有行为；此次改动只解决文案与语言传递。
- 通过模板渲染和捕获的发信请求验证中英文及发起时语言；真实投递单独记录证据，不能把渲染通过算作已送达。

| I5 收尾与升级记录     | 漏译/参数检查、类型检查、边界检查、生产构建、浏览器布局；填写 L01–L09 和冲突登记                                      | I4       | 提交覆盖报告、测试结果、遗漏项和升级注意点；未通过的项明确列出                             |

批次内按页面或领域拆分可独立审查的变更，不把全站迁移合成一次不可核查的大 diff。可复用同一翻译机制，但不为了批量替换搬动或复制整页。

现有账号邮件按 I0 盘点、I1 验证、I2 完成迁移；其他邮件及 CLI/MCP 文案单独记录后续范围。供应商远端介绍和代码生成内容在 I0 分类，其中属于网页可达显示的文案按 I4 覆盖表处理，不因界面完成而声称所有外部输出均已本地化。

## 7. 验收与验证方案

现有 [L01–L09](localization-plan.md#4-独立验收要求) 仍是产品验收依据。补充以下技术检查，各项实际执行证据见全站实施记录：

| 编号 | 场景                                                       | 证据要求                                                                                                                           |
| ---- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| IT01 | 无 Cookie，浏览器/请求头偏好英文                           | 服务端 HTML、`html.lang` 和浏览器首屏均为简体中文，对应 L01/L03                                                                    |
| IT02 | 切英文、刷新、直接打开子页，再切中文；非法/不支持的 Cookie | 合法选择保持，非法值回到中文；保存失败可见，对应 L02                                                                               |
| IT03 | 同一服务实例并发接收中文及英文请求                         | 每次响应与自身语言一致，无跨请求串用，对应 L03                                                                                     |
| IT04 | 首屏资源和浏览器水合                                       | 无语言回跳、水合错误或可见错误语言闪屏；必要资源预先就绪，对应 L03                                                                 |
| IT05 | 编辑中切语言，含未提交剧本及已有页面状态                   | 不丢输入，不重建创作上下文，不触发额外付费生成，对应 L06/L07                                                                       |
| IT06 | 延迟返回的错误、toast、校验、404 和根异常                  | 采用显示时语言；不只覆盖静态菜单，对应 L05                                                                                         |
| IT07 | 缺键、占位符差异、复数及富文本                             | 资源检查准确失败；插值完整且链接/无障碍说明可用，对应 L04/L05/L08                                                                  |
| IT08 | 同数据下切换语言，检查名称、模型、金额和时间               | 只改变显示格式，原文、真实币种、数值与时区语义保持，对应 L06                                                                       |
| IT09 | 中英文桌面与窄屏页面、菜单、弹窗和输入                     | 关键按钮可见，文字不遮挡操作，记录范围和结果，对应 L07                                                                             |
| IT10 | 生产构建、边界、测试/Storybook 运行和 Workerd 占用         | 构建与运行可用，记录依赖和产物/堆增量，不靠猜测判断兼容，对应 L08                                                                  |
| IT11 | 现有账号邮件的中英文/默认语言、发起后切换及并发请求        | 模板与捕获的发信请求含正确主题/正文，异步发送沿用发起语言，无跨请求串用；验证码/链接与原有认证行为保持，对应 L09；真实投递另行记录 |

实施后的常规检查复用 `bun typecheck`、`bun lint`、`bun format:check`、`bun run test` 和 `bun run build`。按改动执行相关边界检查及 Playwright；验证翻译无需实际调用付费模型，涉及动态生成状态时仅复用明确标注的现有 mock/fixture。

如复用 E2E 启动脚本会迁移或初始化本地测试库，应提前核对脚本目标并记录环境；这属于后续实施验证，不在本轮规划中运行。不使用 `bun test` 或 `bun build` 代替项目规定命令。

检查已有测试是否依赖英文可访问名称；通用上游流程可在测试环境显式选择英文以保留原断言，默认中文与中英切换另设专门用例，不通过统一改成宽泛选择器掩盖语言缺陷。

测试结果分别记录“静态/类型”“SSR/浏览器”“真实业务链路”。语言回归通过不等于真实模型生成、支付或商业结算已验收。

## 8. 必要上游改动与升级冲突点

| 拟改位置                                 | 最小修改及原因                                         | 主要影响和升级复核点                                                                 |
| ---------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `package.json`、`bun.lock`               | 增加选定运行时依赖及经验证的开发工具                   | 核对上游依赖升级、许可和锁文件冲突；不顺便升级无关包                                 |
| `src/routes/__root.tsx`                  | 连接首屏语言、文档属性和标题；处理根错误展示           | 上游根布局、head、重定向和异常结构变化时复核，保留原逻辑                             |
| `src/router.tsx`、`src/ui/providers.tsx` | 按 I1 验证结果增加必要实例/Provider 桥接               | 首屏生命周期和现有 query/realtime/observability 不能被重建；最终只改必要入口         |
| 现有语言入口所在的布局/菜单              | 插入复用控件，未登录页面同样可达                       | 上游菜单、导航和响应式布局变化                                                       |
| 各领域页面和组件                         | 静态文案替换为翻译调用，必要格式化                     | 上游文案/参数变化逐处合并，不复制整页形成平行版本                                    |
| `src/ui/query-client.ts` 等提示调用处    | 保持现有错误判断，增加显示时翻译                       | 错误处理、重试和缓存语义不变；上游改错误契约时复核                                   |
| 现有账号邮件发送回调及模板（I0 定位）    | 将发起时校验后的语言传入现有模板，翻译主题及正文等文案 | 上游认证回调、模板、发送接口及参数变化时复核；保持验证码/链接/有效期、认证和发送规则 |
| 测试及 Storybook 的必要组装入口          | 为消费翻译的组件补正确上下文                           | 不全局 mock 掉翻译掩盖缺键；测试预期匹配真实语言                                     |

选择当前首选方案不预设改 `vite.config.ts`、`src/server.ts`、`src/start.ts` 或构建插件。若 I1 发现现有公共接口无法满足，先记录具体缺口及最小改动原因，再在已授权实现范围中处理；不能添加依赖边界豁免来绕过接入问题。

每批交付记录上游原行为、二开动机、实际文件、验证和冲突点。上游基线仍按实际合入提交维护，不因本轮调研改变。
