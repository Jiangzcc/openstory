本次 fetch 只刷新远端引用，没有合入上游，也没有改变 B。U2 相对 B 有 40 个第一父链节点、48 个历史提交。使用 Git `2.53.0.windows.2`，分别将这 40 个节点试合入 E 和 C；同时核对 S，避免混淆首批试点和后续全量实施的效果。

```sh
git rev-list --first-parent --reverse <B>..<U2>
git merge-base --all <E-or-C> <target>
git -c merge.conflictStyle=merge merge-tree --write-tree --name-only --no-messages -z <E-or-C> <target>
```

每一对共同祖先均核实为 B。同一目标采用相同 Git、配置和合并方向；不在节点之间人工解决冲突。`merge-tree` 仅生成 Git 对象，测量期间 HEAD、索引及工作区未变。读取结果树中的冲突文件，按准确匹配两端 SHA 的成对冲突标记统计文本冲突块；无文本标记的冲突仍保留在文件计数中。本轮两个关键目标的冲突均有文本标记。

40 个节点是相互关联的累计版本，不是 40 个独立发布窗口，不能把各行冲突数相加称为“全局唯一冲突数”。路径并集另行去重；文本块和行数也不等同人工解决工时。完整逐节点计数、结果树和原始材料指纹见[机器证据](preservation/20261115-p3-conflict-assessment/comparison.json)。

## 原因与验收纠正

执行重心从减少长期核心接入，逐步偏向差异签收、测试补证，以及根归属、通知、取消、素材发布等可靠性修复。修复有价值，应保留；它们也增加了上游同改区域。把 helper 提取、决策去重或“每个差异都有解释”直接当作升级收益，遗漏了是否真正减少三方合并重叠这一关键检查。

例如 `src/shots/ui/scene-group.tsx` 在 S→C 没有改变，B→S 的翻译接入仍分布在原组件文案和表达式中；局部模型或工作流 helper 整理不会自动消除这类长期重叠。新增冲突同样不能只凭路径认定应删除：共享素材发布与估价修复有各自行为保障，不能为了数字下降直接撤回。

后续 P3 以实际结构整改和合并效果验收，差异台账作为辅助证据：

1. 从全部当前二开差异识别长期职责和重复侵入，保持 UI 国际化、指令语言、模型渠道、组织、钱包及上游执行能力；不再按某次 18 或 54 个冲突文件圈定范围。
2. 每批先指出将退出或缩小的具体上游接入及其职责，再实施单一职责调整。仅移动文件、增加 helper 或修复无关缺陷，不登记为冲突下降成果。
3. 用固定 B、E、U2 及全部 40 个节点复测，报告冲突文件、文本块、路径并集和新增/退出接缝；需要看到冲突下降，不能用另一批测试通过或处置闭合替代。新增上游窗口另列，不移动旧比较分母。
4. 保留功能和原断言的当前验证，与文本冲突减少分别签收。不通过整文件取上游、删减功能、隐藏冲突、实际合入目标或移动基线制造下降；这些做法也不能证明未来升级成本降低。
