# 二开扩展与上游兼容约束

首次记录：2026-11-04；更新：2026-11-08。状态：用户已确认的工程约束；国际化已按授权实施，商业功能仍按具体条目区分已实现与规划。

本约束适用于中文界面及后续全部二开。目标是在完成实际需求的同时，让项目风格一致、改动边界清楚、上游升级可追踪。优先级不代表必须零修改上游，也不允许以“独立扩展”为由复制整套核心实现。

历史二开保真审查、当前缺口修复、接入点收口和后续持续维护的实施顺序见 [上游业务保留与二开长期维护计划](upstream-preservation-plan.md)。Git 历史完整与关键原行为保留分别验收，新增测试不替代上游原有保障。

## 1. 代码风格与目录归属

- 沿用现有命名、格式、导入方式、组件结构、类型及错误处理习惯，遵守项目格式化和检查规则。
- 新职责优先采用独立模块、领域内扩展目录与清晰接口；目录落点依据实际领域及现有结构确定，不先造通用扩展框架或空目录。
- 扩展目录同样遵守客户端/服务端、领域、数据库和工作流边界；不能为隔离二开而放宽平台无领域依赖、ScopedDb 或权限约束。
- 页面只负责展示及适用交互，业务逻辑下沉到服务，请求统一走既有 API 层约定。
- 遵守用户要求的文件、函数、复杂度和嵌套上限；继承的超长上游文件不借当前需求做无关拆分，必要最小改动单独说明。
- 不做与当前需求无关的批量改名、格式化、依赖升级、代码移动或大范围重构。

## 2. 接入方式的优先顺序

| 顺序 | 接入方式                   | 评估要求                                                                     |
| ---- | -------------------------- | ---------------------------------------------------------------------------- |
| 1    | 已存在的公开接口与配置能力 | 先核对实际代码及导出契约，不假设存在未实现的扩展接口                         |
| 2    | 独立模块及领域内扩展目录   | 将新增职责与资源集中，保持依赖方向和关注点清晰                               |
| 3    | 薄桥接层或明确的组装入口   | 只连接上下文、配置或调用，不复制业务流程，也不引入另一套权限/计费判断        |
| 4    | 必要的上游局部修改         | 只有前述方式不能正确完成需求时，修改最小必要接入点，并留下影响与升级冲突记录 |

这是设计优先级，不要求为每个简单需求增加多层抽象。优先使用项目已有的公开导出、服务入口或组合方式；没有满足需求的公开契约时明确记录缺口，不能伪造方法或悄悄依赖内部细节后称为公开 API。

## 3. 对上游行为和数据的限制

- 尽量避免改动上游核心流程和既有数据结构；每次仅处理当前需求所需的职责。
- 界面翻译不修改生成、结算、资源权限或存储语义，不因换语言转换币种。
- 后续模型销售计价、成本核算、禁止 BYOK、默认私有等保留规划可能需要改变既有行为；这类改变必须有需求依据、明确范围和验证。个人独立人民币余额和新增卡密商业改造已于 2026-11-06 取消，不据旧规划安排实现。
- 确需数据结构调整时，先说明为什么扩展接口或模块不能满足，明确最小字段/表/约束变更、存量处理、兼容及迁移验证；不顺便重塑无关实体。
- 不复制大段上游模块形成难以同步的平行实现，不通过全局运行时篡改或页面文本替换绕开真实接入点。
- 单纯重构保持外部行为不变，一次只拆一个职责；业务行为调整与结构性整理分别说明，避免混在无关 diff 中。

## 4. 中文界面的具体应用

- 翻译资源、语言选择与记忆、格式化工具优先组织为独立且符合现有分层的模块。
- 根布局/组装入口只承担必要的语言上下文接入；既有组件只做必要文案、格式化调用和切换控件接入。
- 大量页面需要文案替换时逐页列出实际范围，不能因为改动分散就顺带改写页面业务逻辑或整页复制到扩展目录。
- 不改变用户原文、剧本、生成提示词、模型调用行为、账本数据或实际币种。
- 采用统一翻译机制，语言切换应通过页面实际渲染生效，不通过遍历 DOM 替换英文或修改上游业务结果实现。
- 上游更新新增或变更文案、根布局及公共组件时，核对翻译资源与桥接接入点；漏译、失效或新增冲突必须如实记录。

## 5. 侵入式改动记录要求

确需修改上游时，在对应设计和交付说明中记录以下内容。此表是记录模板，当前没有由本表自动生成的改动或接口。

| 记录项           | 必须说明的内容                                                                       |
| ---------------- | ------------------------------------------------------------------------------------ |
| 原有行为与需求   | 上游原来如何工作，当前需求为什么不能沿用                                             |
| 基线及实际接入点 | 对照的上游提交，拟改或已改的文件、职责、调用位置                                     |
| 原因与替代方案   | 为什么公开接口、独立模块或薄桥接仍不能满足，采用最小改动的依据                       |
| 最小改动范围     | 哪些上游点发生变更，新增模块如何连接，有无数据结构变化                               |
| 影响             | 用户行为、接口契约、权限、计费、工作流、数据兼容等实际受影响项；无影响项简要说明依据 |
| 验证             | 针对变更的检查及结果，哪些仍待验证，不用无关测试数量代替证据                         |
| 升级冲突点       | 上游哪些文件、导出、行为或数据变更可能冲突，合入时需要复核什么                       |
| 已知限制         | 尚未覆盖的兼容情况和必要恢复/迁移边界，不声称未经验证的兼容性                        |

不因为存在这个模板就要求创建额外审批流程。按用户已授权的任务范围工作；后续商业功能的代码实施仍需对应明确任务范围。

## 6. 上游合入时的检查

- 以记录的最近合入基线和实际新版本比较，不因 fetch 自动改变二开基线。
- 分别审查新增模块、桥接接入点和必要上游修改，不能只看新增目录就认为升级无冲突。
- 核对公开接口签名及行为、共享组件与布局、schema/迁移、工作流和权限约束是否变化。
- 对受影响功能执行对应验证；翻译特别检查新增文案、语言持久化、首屏一致性和界面布局。
- 实际合入后再更新基线与冲突记录；未验证的上游升级明确保持待验证。

登录页样例后，现有界面、帮助与账号邮件国际化已有实施，实际范围与验证边界见 [全站国际化记录](localization-implementation.md)；系统指令、管理员模型配置和渠道等后续二开分别见各自实施记录。人民币计价、全面禁止 BYOK 和默认私有等仍是未实施规划。本文件继续约束历史治理与后续开发，不把早期登录页样例状态当成当前全站状态。
