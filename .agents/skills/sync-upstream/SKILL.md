# 上游逐项同步

把上游更新拆成可审查、可恢复的单项工作。每次从当前仓库重新发现二开功能及约束，不依赖固定功能清单、分支名或技术栈。先依据当前用户指令确定是评估、合入还是继续未完成批次，不把历史建议升级成业务要求。

## 开始或恢复

1. 读取当前仓库适用的 `AGENTS.md` 和其引用的项目规则，发现现行需求、架构、二开及历史同步记录的真实位置；文件不存在时不假定固定目录。旧实施记录是案例，不是当前需求或当前测试成绩。
2. 检查目标分支、remotes、工作区、索引和未完成的 merge/cherry-pick。已有未提交内容先确认归属并保留；已有冲突先还原上下文，不能直接 reset、stash 或重新启动合并。核实哪个 remote 是上游、哪个是本项目，不默认必须叫 `upstream`/`origin` 或合入 `develop`。
3. 需要最新上游时 fetch 对应 remote，记录 fetch 结果；网络失败或只有旧引用时明确时效。固定二开起点 SHA、上次实际合入的上游基线 SHA、本轮目标 SHA；恢复批次沿用原起点，不用当前 HEAD 覆盖旧记录。新增更新单独追加评估，不能悄悄移动实施目标。
4. 可使用下方只读脚本列出主线节点、历史提交数量及三方差异候选。范围必须由已核对的 SHA 指定；发现基线不是目标或当前 HEAD 的祖先时先调查。按 [动态二开发现与兼容评估](references/compatibility.md) 建立本轮清单，包含新增、改名、删除和跨文件契约。

```sh
node .agents/skills/sync-upstream/scripts/inspect-range.mjs --base <上游旧基线SHA> --target <固定目标SHA>
```

脚本以执行目录当前 HEAD 为本地侧；先确认处于目标分支对应的 checkout。它不 fetch、不写文件、不更改 Git，会比较当前 HEAD 与目标的共同祖先，列出本地候选差异、待合入上游差异和精确路径交叉；路径不交叉不证明行为兼容。多个共同祖先时不替执行者选择基线。

脚本只依赖 Git 与 Node.js；没有 Node 时使用等效只读 Git 调查，不要求项目安装新运行时或改变技术栈。

## 逐项评估

- 沿上游第一父链由旧到新评估。看每个节点相对第一父提交的净变化，并检查其支线历史中的重要语义；主线节点数与全部历史提交数分开报告。已由 merge 带入的支线提交不重复 cherry-pick。
- 每项记录：上游 SHA/主题、实际变更、关联的本轮二开功能/契约、合入方式、所需适配、定向验证和未验证边界。评估全部不等于合入。
- 在授权范围内沿用项目现有扩展方式和边界。除了同文件冲突，还要从接口、数据、配置、依赖及调用关系识别间接影响；新二开功能通过本轮发现流程进入评估，不要求预先修改技能。
- 维护一份精简进度表，至少区分已评估、待合入、合入中、已合入及验证状态。恢复时先核对表与实际 Git 祖先关系，避免重复合入。

## 获得合入授权后

“开始合入”覆盖已评估范围的逐项合入、必要兼容修复、验证及正常 hooks 的本地提交；推送、PR、部署及外部消费按当前会话的实际授权执行，不重复索取已有授权。

- 默认逐主线节点 `git merge --no-ff --no-commit <节点SHA>`；若现有评估采用其他策略，按其依赖和历史保留要求执行并记录。未解决当前节点前不开始下一节点。
- 主智能体串行操作共享 Git 索引和合并状态；子智能体可以并行只读评估、审查或承担互不重叠的文件。服务、端口和同一测试资源指定一个执行者。
- 每项先审查上游净变化和本地差异，再解决冲突。依赖清单与锁文件一起核对，保留二开额外依赖，不整文件取上游或删除锁文件后无约束重算。
- 完成该项定向验证，明确 stage 本项批准路径，检查 cached diff，使用正常 hooks 提交；不添加工具署名。记录上游 SHA → 本地 merge SHA 与测试证据。直接合入的必要修复可以随该项提交，后续发现的独立修复单独记录。
- 若发现会阻塞后续的真实回归，先修复或明确报告当前阻断，不靠跳过断言继续制造“已验证”状态。尚未具备的目标运行环境如实列为未验证，不自动扩大为部署任务。

## 验证与收尾

按受影响领域选择验证。逐项执行定向检查，在最终集成状态执行适用的全量检查；之后仅因新修改、失败或未决风险复跑相关范围。长回放、失败定位、覆盖统计和恢复环境按 [验证与恢复](references/verification.md) 执行。

采用逐节点 merge 保留历史时，最终结构核对可加二开起点及严格模式：

```sh
node .agents/skills/sync-upstream/scripts/inspect-range.mjs --base <上游旧基线SHA> --target <固定目标SHA> --start <本轮二开起点SHA> --require-complete
```

严格模式核对目标历史全部可达、逐节点 merge 唯一匹配且顺序正确、没有未完成的 merge/cherry-pick。它仍会报告 dirty 文件，且不把工作区有改动等同于合入失败；交付时另核对批准内容已提交、其他用户改动保留。

若已选 squash/cherry-pick 等其他策略，按其提交映射、补丁及语义证据核对，不用逐 merge 检查强行改变已选策略。

实际合入后才更新当前项目的上游基线和实施记录；部分完成时只更新到实际连续合入节点。交付写清上游已有、二开适配、通过/失败/跳过/未验证、首次失败与复跑关系，以及提交和推送状态。本轮新发现的二开职责与升级敏感点写进项目记录，供下轮重新核对。

## 案例不是能力白名单

当前仓库若保留历史合入记录，可按需读取相关实例；缺少旧记录不阻碍使用技能。复用范围固定、三方发现和证据方法，每轮重新确定功能清单、提交数、版本、命令和验证矩阵。不复制旧成绩，也不把某次业务、框架、Mock 错误或修复方式固化成通用要求。
