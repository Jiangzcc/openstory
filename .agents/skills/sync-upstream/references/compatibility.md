# 动态二开发现与兼容评估

本轮需要保护的功能从当前事实推导，不从技能内置清单选择。新增功能即使没有文档、没有独立扩展目录，或只修改上游原文件，也必须能进入候选范围。

## 1. 建立三方范围

固定已确认上游旧基线 B、本轮初始本地起点 L0、上游目标 U；每次调查以当前 HEAD 为本地侧 L。核对 B 是两侧祖先，并查看 L/U 的共同祖先 C。正常未开始合入时 C 通常是 B；恢复部分合入时 C 可能已前进，L0 仍用于核对本轮完整合并序列。

- `B..U` 保留本轮原计划及主线节点序列；不能因恢复工作而丢掉已处理节点的记录。
- 对比 C 与 L，得到当前已提交的本地候选差异；对比 C 与 U，得到仍待整合的上游候选差异。C 的计算只服务调查，不自动改写文档基线或用户授权范围。
- 工作区和索引中的未提交变化单列，核对归属、内容和潜在交叉，不混入已提交二开成绩，也不覆盖它们。
- 多个共同祖先、历史重写、squash/cherry-pick、供应商分支或文档基线不符时，先调查实际关系。可达历史与代码等价不是一回事；脚本不会替代这种判断。

脚本 `threeWay.localDelta`、`pendingUpstreamDelta` 记录修改类型和路径，Git 识别的重命名包含两端；复制仍可能显示为新增，需要阅读来源及契约。`overlappingPaths` 只给精确路径交叉。它们是调查入口，不是完整的二开识别或语义兼容结论。

## 2. 把路径还原为职责和契约

结合候选 diff、本地提交及 PR 说明、当前需求/变更记录、领域文档和测试，按实际行为建立简短清单：

| 本地职责/功能 | 当前需求状态及证据 | 实现、桥接和共享依赖 | 必须保留的行为/数据契约 | 相关测试或证据缺口 |
| ------------- | ------------------ | -------------------- | ----------------------- | ------------------ |

不要求仓库预先有二开登记表。文档缺失时从代码与测试反推，并将不确定点标为待确认；提交标题不能单独证明功能实现。历史合并提交、生成文件、格式差异、废弃功能和已取消规划要分清，不把所有本地独有提交都计作新功能。

对每项上游变更，从实际改动向这些契约追踪：

- **直接影响**：同一路径、被改名/删除的模块、对上游原文件的本地修改，以及扩展接入点。
- **间接影响**：调用方/被调用方、公开导出和类型、认证上下文、数据/事件格式、配置默认、缓存/状态键、任务快照、依赖或代码生成契约。即使两侧没有同文件修改，也可能破坏本地功能。
- **整合机会**：上游新能力是否已覆盖某项二开；比较行为及数据后提出复用或去重建议，不自动删除现有定制。

先按真实变更确定领域和风险，再加载相应项目技能及架构文档。不要为所有仓库强加国际化、模型渠道、组织钱包、某种数据库或框架检查。

## 3. 以当前实现验证契约

沿当前项目公开接口及扩展边界做最小适配，按功能选择反例和验证。例如调用者传入新值、下游却重读旧配置；依赖类型通过、生成代码却改变时间单位；界面可见、真实身份授权或后台订阅却不同。这些是思考方向，不是自动修复模板。

依赖或生成结构发生实质变化时，使用匹配版本、真实配置及隔离输出比较实际 API、字段、单位、约束和运行时。既有差异要追溯来源，不把每个生成器差异都当作本轮必须迁移。技术命令、迁移方式、运行环境及外部操作权限均跟随当前仓库约定。

每项记录上游变化 → 关联本地契约 → 最小处理 → 本轮证据/缺口。若证据互相冲突，先保留事实并调查，不按旧案例强行归类。新发现的二开功能及后续升级敏感点补进项目记录；下一轮仍重新核对，不要求修改本技能。
