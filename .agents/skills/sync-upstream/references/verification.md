# 验证、失败定位与环境恢复

## 先完成低成本定向检查

先从当前项目规则、包管理配置、workspace 和 CI 读取有效命令，不预设包管理器、测试框架或部署平台。最终集成执行适用的 lint、格式、类型、死代码、单测和构建；不因旧结果跳过新修复关联检查，也不在没有新风险时重复整套长测试。

全量并发超时后先隔离失败文件，核对原失败步骤的实际耗时和断言。保留首轮失败及复跑配置；即使隔离通过，也不能写成首轮全量一次全绿，或在未剖析时断言必然是 CPU 原因。发现基线告警时说明范围，不用全局 suppression 消除。

## 长 E2E 的启动条件

先读当前浏览器/集成测试、完整流水线脚本及 CI 真实启动方式，指定一个执行者管理服务和隔离资源；不要让多个代理争用同一数据库或端口。

- 检查测试工具与运行时/浏览器匹配、端口可用、数据库/存储隔离、合成凭证、Mock 地址、录制关闭及必要的完整流程开关。
- 预构建服务或容器要核对最终产物实际加载的配置及资源，不能只看父进程环境；例如 `.env`/`.dev.vars` 可能被复制进产物。输出变量名及必要指纹，避免输出密钥值。
- 先做受控最小业务探针或原套件前置，检查目标结果持久化、子任务及错误日志。跳过核心步骤的“通过”、顶层完成或空错误列表都不足以证明完整流程运行。
- 确认 Mock 覆盖实际调用路径后再启动昂贵套件；不以缺少夹具为由录制真实付费请求或改用生产资源。

## 失败之后先取证

保存每轮独立报告、trace、服务端日志和运行参数，不覆盖旧失败证据。把以下节点放在同一时间线上：UI 操作 → 新请求 → handler → 持久化 → 通知 → 缓存/界面变化 → teardown。先区分准备失败、测试同步、应用回归、夹具回答与运行环境。

| 观察                                          | 下一步                                                                                                                |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 断言失败后才进入 handler，清理后返回 NotFound | 核对清理时序；一次业务提交并等待该次响应后再查持久化，不能用重试点击制造多次写入                                      |
| HTTP 200，但内容没有变化                      | 检查序列化业务结果及真实持久化；200 仅证明传输                                                                        |
| SSE connected/200，但页面不更新               | 核对目标频道订阅、实际通知、缓存键及后续查询；连接打开不代表目标订阅已经注册                                          |
| checkbox 重试导致多次 POST 或反向保存         | 等可用、单次点击、等待该请求完成，再检查目标状态及业务后果                                                            |
| 页面稍晚出现正确内容                          | 用 trace/录屏和正确查询确定时间，有证据后才局部调整预算；若引入慢速环境专用预算，说明默认行为和适用条件，保留内容断言 |
| 顶层通过但子工作流或服务端 ERROR              | 逐条分类并核对 fixture、请求和时间线，保留错误；不能把所有 ERROR 预先归为同一种原因                                   |

若需同步准备状态，以可观测的就绪信号为依据，只重试可证明无副作用或保持业务状态不变的操作，并设置有限次数；不能反复业务提交来赌就绪。测试准备变更不等于修复生产订阅或恢复机制。

为每次长回放明确要解决的失败和结束条件。同一失败未获得新证据或修复时不重复整套；出现新失败先定位再继续。不能为了更好看的成绩追加无关整链，也不能以节省时间为由跳过本次真实回归。

## 分批覆盖的成立条件

串行套件中后续用例被连带跳过时，先检查共享变量和数据依赖。只有目标业务不依赖中间变更时，才在原文件精确筛选必要前置及目标；先用当前测试工具列出实际选中的用例，再执行，保留串行约束、原正文和断言。

统计不同业务用例而不是多轮结果相加；setup、既有 fixme、运行时 skip、flaky 和失败分别列出，保留原始失败链。分批全部覆盖只证明这些用例各自取得通过证据；若需求本来是整链稳定性，仍须整链验收。

## 恢复环境与最终核对

- 修改临时配置之前，记录原文件是否存在，备份原字节，并记录本轮生成内容的 hash；敏感备份放忽略目录，报告不包含密钥。
- 恢复前先退出本轮启动的进程，核对其 PID/端口归属，不结束用户已有服务。只有当前文件等于本轮生成内容或已经等于原备份时才恢复/删除；未知外部改动保留并说明，不能用强制覆盖收尾。
- 复核恢复后的字节、原本不存在文件的删除、服务端口和工作区；构建产物仍为测试配置时明确其用途，不能交作生产部署包。
- 最终核对固定目标及全部历史可达、merge 第二父提交和顺序、未完成合并状态、staged 范围及本轮提交署名。不要改写继承的上游历史来清除历史署名。
- 项目基线随实际合入更新；实施记录对应当前提交和本轮证据。报告包括失败与复跑、告警、未验证环境、残留错误、恢复结果和 push/deploy 状态。

若当前仓库保留历史实施记录，可按需读取相关实例理解因果；不要求存在指定路径，也不复用旧轮次数量、版本和验收成绩。
